# Chibi Security Mode — Security Overview

Security mode ("sentinel") is a third Chibi aspect, alongside Chibi herself and
Thoth. It lets you ask the companion what the machine's security monitor is
doing, in plain language, and have her narrate verdicts as they happen.

This document describes what that mode can and cannot do, what data it touches,
and how it fails. Read the trust boundary section before relying on it.

## What it is

SynapseOS runs **synguard**, a security monitor that observes process events
(exec, open, socket, ptrace, module load, mount, setuid) and reaches a *verdict*
on each. synguard broadcasts window-relevant verdicts on a Unix socket:

    /run/synguard.sock — AF_UNIX SOCK_STREAM, mode 0666

Chibi's `secfeed.py` subscribes to that socket. Each record is a fixed 152-byte
packed struct (`sg_secfeed_msg_t`, defined in `synguard/include/synguard.h`):

| field     | type      | meaning                                  |
|-----------|-----------|------------------------------------------|
| `magic`   | uint32    | `0x53474656` ("SGFV")                    |
| `version` | uint32    | feed version (currently 1)               |
| `pid`     | uint32    | offending process                        |
| `uid`     | uint32    | its user                                 |
| `verdict` | int32     | allow / log / alert / escalate / deny / quarantine |
| `threat`  | int32     | none / low / medium / high / critical    |
| `comm`    | char[16]  | process name                             |
| `reason`  | char[112] | why synguard decided this               |

**The layout is fixed and must stay in lockstep with that header.** `secfeed.py`
checks `magic` and `version` on every record and refuses to parse anything it
does not recognise, rather than narrating misframed bytes as security events.

## The trust boundary — what Chibi can and cannot do

**Chibi is a read-only observer.** She subscribes to the feed and never writes
to it. She cannot allow, deny, kill, or quarantine anything. synguard is the
sole authority; Chibi is a narrator sitting downstream of it.

This is deliberate. The aspect puts an LLM in the loop, and an LLM must not be
able to take security actions:

- Everything she says about security comes from the live `SECURITY STATUS` block
  injected into her prompt, which is generated by `SecFeed.overview()` from real
  feed records.
- Her system prompt forbids inventing processes, verdicts, threat levels, or
  intrusions, and instructs her to report only what that block says.
- If you ask her to block or kill something, she is instructed to say she
  cannot, and to point you at `syn guard`.

Treat her output as a **narration of synguard's decisions, not as an authority on
them**. For ground truth, use `syn guard status` / `syn guard alerts`, or read
synguard's journal directly. If Chibi and synguard ever disagree, synguard is
right.

## Failure modes (an absent monitor is not a safe system)

The most dangerous failure here would be Chibi reassuring you about a machine
nobody is watching. Two distinct states are therefore reported differently:

- **synguard is not running** — `SecFeed.overview()` says the system is *not
  being monitored*, and the prompt explicitly forbids describing an unmonitored
  machine as safe.
- **synguard is running but no verdicts have arrived** — the system is *quiet*.

The sentinel overlay shows `— SENTINEL: NO FEED —` whenever she is not actually
attached to the socket, so a detached feed is visible on screen and not silently
mistaken for calm.

If synguard is not present at all (Chibi running on a non-SynapseOS box, e.g. the
Pi), the socket never appears, the subscriber retries with a backoff, and the
aspect reports the monitor as absent. Nothing crashes and nothing is fabricated.

## What data the aspect touches

Records contain process names, pids, uids, and synguard's reason strings. They do
**not** contain file contents, keystrokes, or network payloads.

Two things are worth knowing:

- **The socket is world-readable (0666).** That is synguard's design — it lets
  the unprivileged compositor colour a window's border on a verdict — but it does
  mean *any* local user can subscribe and observe process names and verdict
  reasons. This is a pre-existing property of synguard, not something Chibi
  introduces; it is noted here because the aspect makes that data conversational.
- **Verdict text reaches the LLM.** In security mode the overview (including
  process names and reasons) is injected into the model prompt. If `llm_backend`
  points at a remote Ollama server, that text leaves the machine. On SynapseOS the
  default is local (`synapd` / localhost), so it does not.

## Using it

Say (or type) any of: **"security mode"**, "enter security mode", "security
overview", "security status", "sentinel", "is the system safe".

While in the aspect:

- She opens with the current overview and then narrates *notable* verdicts as
  they land — alert, escalate, deny, quarantine, or anything at medium threat or
  above. Routine allow/log traffic is never announced; it would be a constant
  murmur. A burst of verdicts collapses into a single utterance rather than a
  burst of speech.
- Say **"status"**, "overview", or "report" to re-read the live feed directly,
  without a round-trip through the LLM.
- Say **"stand down"**, "exit", or "chibi mode" to leave.

The screen goes bare and dark — no stars, no neon grid, no weather. The border
breathes amber, and turns red and pulses fast once synguard has actually blocked
something, so the frame colour reflects real state rather than decoration.

Set `security_enabled = False` in `config.local.py` to disable the aspect
entirely, or `security_announce = False` to keep it silent until asked.

## Note on the trigger

Horus mode treats *any* short utterance ending in "mode" as its entry phrase,
because Whisper-tiny cannot reliably transcribe the proper noun "Horus". That
means "security mode" would open the dream journal. `_check_security_triggers()`
therefore runs **before** `_check_horus_triggers()` in `handle_input()`. Do not
reorder them.
